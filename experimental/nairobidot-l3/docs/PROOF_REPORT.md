# Punkti 0.6 Layer 3 — clean-room interoperability proof

Status: **evidence for founder review. Nothing is frozen. No deployment.**
Branch: `proof/punkti-0.6-cleanroom` (isolated, not merged, not deployed).
Task: CEO-OS Issue #11 — "Punkti 0.6 — clean-room Layer-3 interoperability proof".

## 1. Answer to the architecture test

> Can I implement Punkti Layer 3 without implementing Punkto, BRTH, human identity,
> AI identity, news semantics or any application schema?

**YES.**

Evidence:

- The implementation (`src/nairobidot/`) was written in an isolated directory that
  contained only the two normative documents (`PUNKTI_0_6_LAYER3_RESET.md`,
  `PUNKTI_0_6_MESH.md`) and an implementation brief. No reference source, no Punkto
  application code, no BRTH material, no identity schema was present or consulted.
- `interop/test_interop.py::test_no_reference_imports` statically scans every clean-room
  source file for reference imports (`import carrier`, `import mesh`, `import spatial`,
  `punkti-v0.6-mesh`) and asserts the package imports in an isolated interpreter with
  only `experimental/nairobidot-l3/src` on `sys.path` and no reference modules loaded.
- The harness never exposes a semantic concept: `x` is opaque text, `refs` are opaque
  strings, `ext` is opaque bytes, `alg` is dispatched explicitly, and no code path parses
  `x` (grep-verifiable in `src/nairobidot/`). Spatial selection reads only `h`.
- The implementation required **no application, identity, or news concept** to pass every
  carrier, spatial, sync, convergence and interop test. Nothing in it is Punkto-specific.

Data-layer rejection parity (both implementations agree, verified over real HTTP):
forged signature → `INVALID-provenance`; byte-flipped `R`, trailing bytes, truncated `R`,
non-canonical base64, duplicate keys *inside an atom envelope* → `INVALID-structural`;
unsupported `alg` → `UNVERIFIABLE-alg` (retained as candidate, never in the main store);
future-version wrapper → `OPAQUE-version`; and a forged signature arriving before the valid
record at the same MID never suppresses the valid record.

## 5. Divergences found (all at the unspecified HTTP boundary, none in carrier bytes)

Seven request-validation behaviours differ. Both implementations are defensible readings of
`PUNKTI_0_6_MESH.md`; the document does not specify an HTTP request-validation table.
They are pinned as tests (`http_duplicate_key_divergence`, `request_validation_divergences`)
so a spec correction can be checked against them later.

| Case | Reference | Clean-room |
|---|---|---|
| `/push` body with duplicate `records` member | HTTP 200, last key wins, record admitted | HTTP 400 `kind=request`, nothing stored |
| `/pull` scope with equal h bounds (`h_lo == h_hi`) | HTTP 400 `empty/reversed h interval` | HTTP 200, empty page |
| `/pull` scope with reversed elevation | HTTP 400 `empty/reversed z interval` | HTTP 200, empty page |
| `/pull` scope with equal elevation bounds | HTTP 400 `empty/reversed z interval` | HTTP 200, empty page |
| `/pull` query with an unknown member | HTTP 200, member ignored | HTTP 400 `reason=query-fields` |
| `/push` item declaring a wrong address for a VALID record | HTTP 400 for the whole request | HTTP 200, per-record `INVALID-structural` `address-mismatch` |
| `/push` with an empty `records` list | HTTP 400 `push batch size` | HTTP 200 `{"results":[]}` |

These do not affect honest peers exchanging valid records, do not change any MID, address,
canonical body, signature or validation state, and do not affect spatial selection of valid
records. They do affect error handling and a strict peer's tolerance for an empty batch.

## 6. Proposed minimal corrections (only where an implementer cannot converge)

1. **Publish the numeric conformance vectors in the spec.** Issue #11 asks to reproduce
   "normative vectors"; the Reset deliberately leaves numeric vectors to a freeze task, so
   none exist to reproduce. Minimal fix: move the six vectors in §3 (C, S, MID, address, R,
   signature, plus one legacy v0.5.1 fixture) into the L3 document as an appendix. Without
   this, "interoperable" is only checkable against a running reference, not the text.
2. **Add the HTTP request-validation table** to the Mesh document: duplicate JSON member
   names (reject, per the envelope rule), empty/reversed/equal interval bounds, unknown
   query members, declared-address mismatch, and empty PUSH batches. This closes all seven
   divergences in §5 with one paragraph and no wire change.
3. **State that any non-empty `h` carries 20 altitude bits and there is no absent-Z
   sentinel**; horizontal-only selection is expressed by omitting `z_min`/`z_max`. Both
   implementations agreed here only because the provisional formula is fully specified.
4. **Name the canonical JSON profile for the cursor `scope` digest** (or state explicitly
   that tokens are opaque and MUST NOT be recomputed or compared across implementations).
   The current wording ("canonical sorted compact JSON") is not a standard and is the most
   likely place for two independent stores to disagree on token binding.
5. **Specify the MID-mode `ceiling` representation** (this implementation uses the local
   append-sequence high-water for both modes; another store could use a snapshot id or the
   maximum `(address, digest)` pair).
6. **Make the `/hello` member and limit names normative** (`protocol`, `epoch`,
   `subscriptions`, `peers`, `capabilities`, `limits.*`) and pin the `capabilities` tokens.
   Both implementations happened to choose similar names; capability negotiation otherwise
   depends on convention.
7. **Define candidate-store `admitted` semantics** (whether retaining an unverified record
   counts as admitted). This implementation reports `true` with the true local state; a peer
   could report `false`.

No carrier, envelope, canonical-bytes, MID, signature, provenance, spatial, or cursor
mechanism needs to change.

## 7. What remains unfrozen

Nothing in this work freezes or authorizes anything. Specifically still open:

- the wire format itself (the Reset is explicitly "proposed", not normative);
- canonical encoding and framing details, domain-separation literals, version/algorithm
  spellings, timestamp bounds;
- the geohash/altitude profile (60-bit interleaved provisional profile, cell-centre
  altitude formula) and whether altitude is mandatory in every non-empty `h`;
- reference syntax/order rules, extension rules, key/signature formats for any algorithm
  other than classic Ed25519;
- admission limits, variant retention policy, candidate capacity, page/HTTP byte budgets;
- future-version opaque wrapper grammar and transport rules;
- cursor token internals and MID-mode ceiling type;
- the HTTP request-validation table (§6.2);
- the legacy v0.5.1 adapter: deliberately **not** implemented here (Mesh states no legacy
  adapter is advertised); legacy fixtures and the `UNVERIFIABLE-key` path remain open;
- production concerns: durable storage, TLS/peer authentication, rate limiting, deletion and
  retention, multi-hop/partition guarantees (explicitly not promised by the spec).

No v0.6 freeze, no merge, no production deployment, no change to `pwa/`, `relay/`,
`deploy/`, or any frozen v0.5.1 artefact was made by this task.

## 8. Reproduce

```bash
# clean-room unit tests (23)
PYTHONPATH="$PWD/experimental/nairobidot-l3/src" \
  python3 -m unittest discover -s experimental/nairobidot-l3/tests -v

# reference baseline (27)
python3 -m unittest discover -s experimental/punkti-v0.6-mesh/tests -v

# black-box interop matrix (13) — regenerates interop_matrix.md + interop_report.json
python3 experimental/nairobidot-l3/interop/test_interop.py -v
```

Loopback HTTP only; no external service, no network access beyond `127.0.0.1`.
